The big picture and architecture

The problem: when a doctor wrote an ordonnance, they typed every medicine name by hand. The goal: suggest medicines from the official Moroccan list published by the AMMPS (Agence Marocaine du Médicament et des Produits de Santé), about 9,950 medicines.

The key architecture decision: three kinds of database

Cabinova gives each cabinet its own database (database-per-tenant). But the medicines list is the same for everyone, so copying it 100 times makes no sense. We added a new shared database:

Platform DB

Cabinets, subscriptions, Super Admin users, audit log.
Already existed. In clinic-api it's called CATALOG.

Medicines DB (new)

The national AMMPS list plus the history of imports.
One for everyone. Only admin-api writes to it; cabinets only read.

Each cabinet's DB (tenant)

Patients, ordonnances… and now each doctor's settings and own medicines.
Linked to the medicines list by ammps_id only.
Why not link them with a foreign key? Because they really are separate databases, and Postgres can't link tables across two databases. So the link lives in the code (the service layer): we read from both databases, then merge the results in JavaScript by ammps_id.

Why "medicines database" and not "catalog"?

The original request called it a catalog, but in clinic-api that word already means the platform database (CatalogService). Using the same name would have caused dangerous confusion, so we chose MEDICINES_DATABASE_URL and @cabinova/medicines-db.

The four golden rules

  1. Doctors never write to the shared medicines database.
  2. The import never writes to cabinet databases.
  3. A medicine is never deleted: one that disappears from the file only becomes "inactive", because old ordonnances may still point to it.
  4. A printed ordonnance line is a snapshot: it never changes, even if the list changes later.

Second table: medication_imports

One row per import: file name, who ran it, status (running / success / failed), how many medicines were added, updated and deactivated, and why it failed, if it did.

Fast search: the pg_trgm extension

We added trigram indexes on the name and the substances. That's what makes searching by part of a word very fast: typing "lipr" finds DOLIPRANE.

CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX "medications_name_trgm_idx"
  ON "medications" USING gin ("name" gin_trgm_ops);

Step 2

Reading the AMMPS Excel file

File apps/admin-api/src/medicines/ammps-file.ts: a "pure" function that takes the file's bytes and returns clean rows, with no database involved. That makes it very easy to test.

How is an xlsx file read?

An .xlsx file is actually a ZIP file of XML files. We used a small library, fflate, to unzip it, then read the XML ourselves:

  1. xl/workbook.xml tells us the first sheet.
  2. xl/worksheets/sheet1.xml holds the cells, row by row.
  3. Text can sit inside the cell itself (inlineStr, like your file) or in a shared list, sharedStrings.xml (when saved from Excel). Both are supported.

Cleaning rules

  • Columns are found by their header, not their position, ignoring case, accents and "(DH)". Required columns: ID AMMPS, Nom commercial, Substance active.
  • Prices: parsePrice understands every format: 
    "4.303.00 DH"  → "4303.00"
"10,70 DH"     → "10.70"
"1.200,50 DH"  → "1200.50"
"SANS PPV DH"  → null
  • Status: availabilityOf maps 10 different statuses to 3 categories (for example "Retiré" and "Suspendu" become withdrawn).
  • Bad lines don't stop everything: a line without a valid ID is skipped, with its line number and the reason. A repeated ID keeps its first line.
Protection against "bombs"Files over 20 MB are refused, and so is any file that would become huge once unzipped (a zip bomb).
Result on your real file9,947 medicines in 0.2 seconds, zero lines refused: 5,217 marketed, 3,861 not marketed, 869 withdrawn. 27 unit tests.
Step 3

The import: all or nothing, with a safety rule

File apps/admin-api/src/medicines/ammps-import.ts.

How it works (inside one transaction)

  1. Create a temporary table, ammps_rows, and copy the file into it in batches of 1,000 rows.
  2. Add: every medicine not yet in the list gets an INSERT.
  3. Update: only what really changed (using IS DISTINCT FROM), so "last updated" stays meaningful.
  4. Deactivate: every active medicine missing from the file gets is_active = false. Never a delete.
  5. A deactivated medicine that comes back in a later file is reactivated.
Why a transaction?If an error happens halfway, Postgres cancels everything automatically (rollback). The list is either fully updated or stays exactly as it was. There's never a "half-imported" state.

The safety rule (the most important part)

Before changing anything, the file is refused if:

  • it holds fewer than 80% of the currently active medicines (a cut-off file? the AMMPS site down?);
  • more than 5% of its lines can't be read (the file's format changed?).

Without this rule, one incomplete file could deactivate thousands of medicines for every cabinet in a second.

One import at a time

We used a "partial unique index": the database itself refuses two rows with the status running.

CREATE UNIQUE INDEX medication_imports_one_running_idx
  ON medication_imports (status) WHERE status = 'running';

And if an import is cut off by a server restart, it's released automatically after 15 minutes.

The command-line command

pnpm --filter admin-api medicines:import ~/Downloads/medicaments-ammps.xlsx
On your fileFirst run: 9,947 added. Second run: 0 changes. Under two seconds each. 7 e2e tests cover every case.

Step 5

Each cabinet's tables: the doctor's settings

Migration 0041_medication_overrides in packages/tenant-db.

The medication_overrides table

The doctor's own version of an AMMPS medicine:

  • custom_name, custom_dosage: their own name and dosage ("Doliprane" instead of "DOLIPRANE"). An empty field means "as the AMMPS says".
  • default_posology, default_duration: the usual posology and duration, filled in automatically.
  • is_favorite, is_hidden: favorite, or hidden from suggestions.
  • base_name, base_dosage: the AMMPS name and dosage at the moment of saving. The clever part: if the AMMPS changes the name later, we compare and know there's an update the doctor should see.

The custom_medications table

Medicines that aren't in the list (magistral preparations, imported products). One doctor can't add the same name and dosage twice.

An ordonnance line

type PrescriptionItem = {
  medication: string;        // the printed text — never changes
  posology: string | null;
  duration: string | null;
  ammpsId?: number | null;            // new: where it was picked from
  customMedicationId?: string | null; // new
};
Why no data migration?Lines are already stored as JSON (jsonb). We only added two optional fields. Old ordonnances stay exactly as they were.
Step 6

The search API in clinic-api

Files in apps/clinic-api/src/medications/.

A read-only connection

In database/medicines.module.ts, every new connection runs:

set default_transaction_read_only = on

Even if clinic-api were given a URL with write rights by mistake, it couldn't change the list. A test confirms it.

The merge logic: merge.ts (pure functions)

  • Grouping boxes: the AMMPS lists each box size as a separate row (Amlor 10 mg appears 3 times). We group by (name, dosage, form) and pick the cheapest marketed box to stand for the group.
  • Applying overrides: the doctor's name wins, and hidden medicines are dropped.
  • Never suggested: withdrawn or inactive medicines.
  • Order: favorites first, then names starting with what was typed, then a word in the name, then the substance, then marketed before not marketed, then alphabetical.
  • "Updated by the AMMPS": only when the AMMPS changed something the doctor had renamed.

Step 7

Autocomplete inside the ordonnance

medication-input.tsx (the field) and prescription-editor.tsx (the editor) in clinic-web.

What the doctor sees while typing

  1. ⭐ Favorites first, with their usual posology in italics.
  2. AMMPS medicines: name and dosage, form, substance, number of boxes, lowest price.
  3. Their own medicines (tagged "Perso").
  4. "Déjà prescrits": what they wrote before.
  5. "Ajouter « … » à mes médicaments" for anything typed.

Navigate with ↑ ↓ Enter Esc. After picking: the line fills in, the usual posology is added, and the cursor moves to the posology field.

Techniques worth knowing

  • 200 ms debounce: no request on every keystroke, only once the doctor pauses.
  • React Query: caches results (staleTime of 60 seconds), and keepPreviousData keeps the old list visible while loading, so it doesn't flicker.
  • Two buttons on a picked line: ⭐ favorite, and 🔖 "keep this posology as the usual one".
  • Renewal: before copying an old ordonnance we call check-renewal, and withdrawn lines get an amber label.
  • Editing the text by hand breaks the link: the line becomes free text.

An Arabic lesson: isolating Latin text (bidi)

In the Arabic interface (right to left), "Crème magistrale urée 10 %" came out as "% 10 Crème…". The cause: the Unicode bidirectional algorithm (Bidi) reorders neutral characters such as % and digits. The fix: wrap names in a <bdi> element, which isolates the text's direction:

<bdi>{nameOf(c.name, c.dosage)}</bdi>

A search request, end to end

The doctor types "doliprane 1g" in the ordonnance. What happens?

  1. The field waits 200 ms after the last keystroke (debounce), then sends GET /api/medications/search?q=doliprane 1g.
  2. Next.js passes the request to clinic-api, which finds the cabinet from the subdomain and opens its database.
  3. It checks that the user is a doctor (assertMedical).
  4. It splits the text into words: ["doliprane", "1g"]. Each word must appear in the name, the substance, the form or the dosage (the dosage is compared without spaces, so "1g" matches "1 G").
  5. From the cabinet database: the doctor's own medicines, plus overrides matching their own names.
  6. From the medicines database (read only): matching active, non-withdrawn medicines, then all their boxes.
  7. From the cabinet database again: the doctor's overrides for those medicines.
  8. mergeCatalog groups the boxes and applies the overrides, then rankSuggestions sorts and keeps 20.
  9. The interface shows the list. Once a medicine is picked, the line is saved with its ammpsId automatically after 800 ms.

Concepts worth understanding

Database per tenant

Each cabinet has its own database: medical data is fully isolated.

Snapshot

We store the text as it was printed. Later changes never touch the past, which matters legally for ordonnances.

Override

A layer on top of the official data: an empty field means the official value.

Soft delete (is_active)

Deactivate instead of deleting, so old references never break.

Transaction

A group of operations that all succeed or are all cancelled.

Staging table

A temporary table we copy the file into, then compare with fast set-based SQL.

Partial unique index

A uniqueness rule on some rows only (here: those with status running).

pg_trgm

Splits text into 3-letter pieces to make searching by part of a word fast.

Pure function

No side effects: the same input always gives the same output. Easy to test.

Read-only session

A second layer of protection on top of the role's permissions.

Debounce

Waiting for typing to pause before sending a request.

Bidi isolation

<bdi> keeps Latin text from being scrambled inside an Arabic page.

Bugs we found, and the lessons

All of them showed up only when trying things for real in the browser, even though the automated tests were passing.

Production checklist

  • Create a new Neon database for the medicines, and put its owner URL in apps/admin-api/.env as MEDICINES_DATABASE_URL.
  • Create a read-only role (SQL in the README) and put its URL in apps/clinic-api/.env.
  • Run pnpm --filter admin-api db:seed for the new permissions.
  • Fill the list: pnpm --filter admin-api medicines:import <file.xlsx>.
  • Apply migration 0041 to the cabinets with Migrer (together with the pending 0030–0040).
  • Then, every month: upload the new file from Super Admin › Médicaments.
