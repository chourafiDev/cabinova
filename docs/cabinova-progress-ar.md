# Cabinova: ملخص ما تم إنجازه

> آخر تحديث: 15 أكتوبر 2026

---

## 1. فكرة المشروع

**Cabinova** منصة SaaS لتسيير العيادات والمراكز الطبية الخاصة. كل عيادة هي **tenant** مستقل، ولها رابط فرعي خاص بها، مثلاً `clinique-x.cabinova.ma`.

النسخة الأولى (V1) تشمل:

- الفريق والأدوار والصلاحيات
- المرضى
- الأجندة (المواعيد)
- الاستشارات والملف الطبي

---

## 2. التقنيات المستعملة

| الجزء | التقنيات |
|---|---|
| Backend | NestJS 12، PassportJS، Drizzle ORM، PostgreSQL على Neon |
| Frontend | Next.js 16، shadcn/ui، TypeScript، Zustand، TanStack Query و Table، nuqs |
| التصميم | نفس نظام تصميم لوحة تحكم **Noria**، واللون الرئيسي `#613f75` |
| الأجندة | مكتبة **big-calendar** (رخصة MIT)، معدّلة للفرنسية ولأسبوع يبدأ يوم الإثنين |

---

## 3. هيكل المشروع

المشروع **monorepo** يُدار بـ pnpm:

```
cabinova/
├── apps/api   ← NestJS (المنفذ 4000)
├── apps/web   ← Next.js (المنفذ 3000)
└── docs/      ← التوثيق
```

---

## 4. تعدد المستأجرين (Multi-tenant)

- **قاعدة بيانات واحدة مشتركة.** كل جدول خاص بالعيادات فيه عمود `tenant_id`.
- **عزل البيانات عبر PostgreSQL RLS:** كل استعلام يمرّ عبر `withTenant()`، وهي تحدد `app.tenant_id` داخل المعاملة (transaction). بدون هذا المتغير لا يظهر أي سطر.
- **دور خاص بالتطبيق اسمه `cabinova_app`:**
  - التطبيق يتصل بقاعدة البيانات عبر هذا الدور.
  - السبب: دور Neon الافتراضي `neondb_owner` يتجاوز RLS.
  - دور المالك يُستعمل فقط للـ migrations والـ seed.
- **تحديد العيادة من الرابط الفرعي:**
  - المتصفح يرسل الطلبات إلى `/api/*`، و Next يحوّلها إلى NestJS مع ترويسة `X-Forwarded-Host`.
  - NestJS يستخرج الـ slug من هذا الرابط ويبحث عن العيادة (مع cache قصير).
  - إذا كانت العيادة غير موجودة: خطأ 404. إذا كانت موقوفة: خطأ 403.
- **جداول عامة (control plane) بدون RLS:** `tenants` و `roles` و `permissions` و `role_permissions`.
- **فحص RLS تلقائي:** الأمر `pnpm db:migrate` يفرض RLS على كل جدول جديد بعد تطبيق الـ migrations.

## 5. المصادقة والصلاحيات

### تسجيل الدخول

- تسجيل الدخول بـ **جلسات محفوظة في قاعدة البيانات** (وليس JWT).
- الكوكي `cabinova_session` من نوع httpOnly.
- لا يُحفظ في القاعدة إلا الـ hash (SHA-256) الخاص بالـ token.
- إلغاء جلسة أو تغيير صلاحية يُطبَّق في الطلب الموالي مباشرة.
- كلمات المرور مشفّرة بـ **argon2**.
- محاولات الدخول محدودة: 5 محاولات في الدقيقة.

### الأدوار والصلاحيات

- **الأدوار يحددها مدير المنصة (super-admin)**، وهي مشتركة بين كل العيادات:
  - Administrateur
  - Médecin
  - Infirmier / assistant
  - Réceptionniste
  - Comptable
- **الصلاحيات** على شكل `ressource:action`، مثلاً `patients:write` أو `emr:read`. عددها 16 صلاحية.
- **الصلاحيات الفعلية للمستخدم:**
  > صلاحيات أدواره + الصلاحيات الممنوحة له − الصلاحيات المرفوضة عليه
  >
  > الرفض (deny) له الأولوية دائماً.
- **الحماية في الـ API:**
  - `@RequirePermissions()` على كل route.
  - `@Public()` للمسارات المفتوحة.
- **الحماية في الواجهة:** إخفاء القوائم والأزرار حسب الصلاحيات.

## 6. الوحدات المنجزة

### 6.1 الفريق (`/staff`)

- **دعوة عضو جديد:** الاسم، البريد الإلكتروني، ودور واحد أو أكثر.
  - يُنشأ رابط دعوة صالح 7 أيام ولمرة واحدة.
  - **يُرسل الرابط تلقائياً بالبريد الإلكتروني** عبر خدمة **Resend**، مع نسخة احتياطية: الرابط يظهر أيضاً في الواجهة لنسخه يدوياً عند الحاجة.
  - بدون مفتاح Resend (`RESEND_API_KEY` في `.env`)، لا يُرسل البريد فعلياً، ويُكتفى بتسجيله في سجل الخادم (console) — مفيد في التطوير.
  - نفس الشيء عند توليد رابط جديد لعضو موجود: بريد "دعوة" إذا لم يختر كلمة مرور بعد، أو بريد "إعادة تعيين كلمة المرور" إذا كان له حساب نشط.
- **صفحة `/invite/[token]`:** العضو يختار كلمة المرور ثم يدخل مباشرة.
- **تعطيل أو إعادة تفعيل عضو:** عند التعطيل يُفصل فوراً من كل جلساته.
  - لا يوجد حذف، للحفاظ على السجلات.
- **صفحة الصلاحيات لكل عضو:**
  - اختيار الأدوار.
  - لكل صلاحية ثلاث حالات: **Rôle / Autoriser / Refuser**.
  - تظهر الصلاحية النهائية، ومن أي دور جاءت.
- **حماية:** المدير لا يستطيع تعديل صلاحياته الخاصة أو تعطيل نفسه.

### 6.2 المرضى (`/patients`)

- **بيانات الملف الإداري:** الهوية، البطاقة الوطنية (CIN)، الهاتف، العنوان، والتغطية الصحية.
  - التغطية: CNSS، CNOPS، AMO Tadamon، FAR، أو تأمين خاص.
  - جهة اتصال في حالة الطوارئ.
- **رقم الملف:** متسلسل لكل عيادة (N° 00001، 00002…)، ولا يتكرر حتى عند الإنشاء المتزامن.
- **CIN واحدة = ملف واحد** في نفس العيادة.
- **البحث:** بالاسم (بأي ترتيب)، بالهاتف (بدون مسافات)، بـ CIN، أو برقم الملف.
- **الأرشفة بدل الحذف:** لا تُحذف الملفات الطبية أبداً، والملف المؤرشف للقراءة فقط.
- **الفلاتر:** الجنس، التغطية الصحية (Couverture)، وتاريخ الإنشاء (Créé le، بفترة زمنية).
- **التحديد الجماعي (Sélection multiple):**
  - مربعات اختيار (checkboxes) في كل سطر، مع "تحديد الصفحة" و"إلغاء كل التحديد".
  - **Exporter CSV:** تصدير الملفات المحددة في ملف CSV متوافق مع Excel، يشمل كل الحقول الإدارية.
  - **Supprimer:** حذف نهائي، لكن **فقط للملفات التي ليس لها أي موعد أو استشارة**. الملف الذي له تاريخ طبي يبقى محفوظاً (يُنصح بأرشفته بدل حذفه)، وتوضّح الرسالة عدد المحذوف والمحفوظ.
  - الصلاحية الجديدة `patients:delete` مطلوبة لرؤية زر الحذف؛ وهي ممنوحة افتراضياً لدور Administrateur فقط.
- **الواجهة:**
  - جدول Noria مع الفلاتر والترتيب والتقسيم إلى صفحات.
  - نموذج من عمودين، مع شريط "تعديلات غير محفوظة".
- **صفحة المريض فيها ثلاثة تبويبات:**
  1. **Dossier:** البيانات الإدارية.
  2. **Rendez-vous:** المواعيد القادمة والسابقة، مع زر "Prendre rendez-vous".
  3. **Consultations:** الاستشارات والسوابق المرضية.

### 6.3 الأجندة (`/appointments`)

- **خمسة عروض:** يوم، أسبوع، شهر، سنة، وقائمة. كلها بالفرنسية، بنظام 24 ساعة، والأسبوع يبدأ يوم الإثنين.
- **حفظ الحالة في الرابط:** العرض والتاريخ والطبيب المختار تبقى في الرابط.
- **حالات الموعد** (كل حالة بلون):

  | الحالة | المعنى |
  |---|---|
  | Planifié | مخطط |
  | Confirmé | مؤكد |
  | En salle d'attente | في قاعة الانتظار |
  | Terminé | منتهٍ |
  | Absent | غائب |
  | Annulé | ملغى |

- **منع الحجز المزدوج للطبيب:**
  - قفل (advisory lock) يضمن أن عمليتي حجز في نفس الوقت لا تأخذان نفس الوقت.
  - الموعدان المتتاليان مسموح بهما.
  - المواعيد الملغاة أو الغائبة تحرّر الوقت.
- **حجز موعد:**
  - بالضغط على خانة فارغة، أو بزر "Nouveau rendez-vous".
  - البحث عن المريض بالاسم أو الهاتف أو CIN أو رقم الملف.
  - اختيار الطبيب، التاريخ، الساعة، المدة، والسبب.
- **نقل الموعد بالسحب والإفلات (drag & drop):** للمستخدمين الذين لديهم صلاحية الكتابة فقط.
- **نافذة تفاصيل الموعد:**
  - زر سريع للخطوة الموالية: "Patient arrivé" ثم "Terminer".
  - قائمة لتغيير الحالة، وزر للتعديل.
  - زر "Démarrer / Voir la consultation".
- **الأطباء:** هم الأعضاء النشيطون الذين لديهم دور **Médecin**.

### 6.4 الاستشارات والملف الطبي (`/consultations`)

- **السوابق المرضية (Antécédents):** ملف واحد لكل مريض.
  - فصيلة الدم، الحساسية (تظهر بالأحمر)، الأمراض المزمنة، العلاجات الحالية.
  - السوابق الطبية، الجراحية، والعائلية.
- **محتوى الاستشارة:**
  - السبب.
  - **العلامات الحيوية:** الوزن، الطول، الحرارة، الضغط، النبض، SpO₂، السكر في الدم.
    - تُحسب **IMC** تلقائياً.
    - تُقبل الفاصلة في الأرقام العشرية، مثل `37,4`.
  - Anamnèse، Examen clinique، Diagnostic، Conduite à tenir.
- **دورة حياة الاستشارة:**
  - **En cours:** قابلة للتعديل.
  - **Clôturée:** مقفلة نهائياً، ويصبح الموعد المرتبط بها "Terminé" تلقائياً.
- **طرق البدء:**
  - من الأجندة.
  - من صفحة المريض.
  - موعد واحد = استشارة واحدة. الضغط مرتين لا ينشئ نسخة ثانية.
- **قيود:**
  - العلامات الحيوية لها حدود معقولة، تكشف أخطاء الكتابة (مثل 750 كغ).
  - لا استشارة لموعد ملغى، ولا لمريض مؤرشف.
- **الخصوصية:**
  - البيانات الطبية **منفصلة** عن الملف الإداري، ومحمية بصلاحيات `emr:*`.
  - موظف الاستقبال لا يرى السوابق ولا الاستشارات.

### 6.5 واجهة الاستخدام

- **بطاقة مساعدة في أسفل القائمة الجانبية:** أيقونة، عنوان "Besoin d'aide ?"، وزر "Contacter le support" (بريد إلكتروني للدعم).
  - تختفي تلقائياً عندما تُطوى القائمة الجانبية إلى أيقونات فقط.

## 7. سجل التدقيق (Audit log)

الجدول `audit_logs` يسجّل: من فعل ماذا، على أي سجل، ومتى.

- **المرضى:** الإنشاء، التعديل (أسماء الحقول المعدّلة فقط، بدون قيمها)، الأرشفة، والاسترجاع.
- **المواعيد:** الإنشاء، التعديل، النقل، وتغيير الحالة.
- **البيانات الطبية:** كل **فتح لاستشارة** وكل **قراءة للسوابق المرضية**، لأن البيانات صحية وحساسة.

## 8. التشغيل

### متغيرات البيئة (`apps/api/.env`)

| المتغير | الاستعمال |
|---|---|
| `DATABASE_URL` | الدور `cabinova_app`، يستعمله التطبيق |
| `DATABASE_MIGRATION_URL` | دور المالك، للـ migrations والـ seed |
| `ROOT_DOMAIN` | النطاق الرئيسي، `localhost` في التطوير |
| `TRUST_PROXY` | `loopback` في التطوير |
| `SEED_ADMIN_EMAIL` و `SEED_ADMIN_PASSWORD` | حساب مدير العيادة التجريبية |
| `RESEND_API_KEY` | مفتاح خدمة Resend لإرسال البريد (الدعوات، إعادة تعيين كلمة المرور). فارغ = البريد يُسجَّل فقط في console |
| `EMAIL_FROM` | عنوان المرسل، افتراضياً `Cabinova <onboarding@resend.dev>` (عنوان تجريبي من Resend) |

### متغيرات البيئة (`apps/web/.env.local`)

| المتغير | الاستعمال |
|---|---|
| `API_URL` | عنوان الـ API: `http://localhost:4000` |

### الأوامر

```bash
pnpm install
pnpm --filter api db:migrate   # الـ migrations + فرض RLS
pnpm --filter api db:seed      # الصلاحيات + الأدوار + العيادة التجريبية
pnpm dev                       # تشغيل api و web معاً
```

بعد التشغيل، افتح العيادة التجريبية على: **http://demo.localhost:3000**

## 10. ما تبقّى (الخطوات القادمة)

1. **الوصفات والوثائق:** ربطها بالاستشارة وطباعتها بصيغة PDF.
2. **الفوترة والصندوق:** الفواتير، والأداء، والترقيم المتسلسل.
3. **لوحة القيادة:** إحصائيات حقيقية بدل الأصفار، مع احترام الصلاحيات.
4. **الإعدادات:** ساعات العمل، شعار العيادة، والقوالب حسب التخصص.
5. **إنشاء حساب Resend فعلي:** حالياً لا يوجد مفتاح `RESEND_API_KEY`، فالبريد يُسجَّل فقط في console ولا يصل فعلياً. يحتاج الأمر حساب Resend (مجاني للتجربة) ثم لاحقاً توثيق نطاق `cabinova.ma` لإرسال احترافي.
6. **إشعارات أخرى:** تذكير المرضى بالمواعيد عبر بريد أو SMS.
7. **بوابة المريض:** حجز المواعيد والاطلاع على الوثائق.
8. **مدير المنصة (super-admin):** إنشاء العيادات تلقائياً، الاشتراكات، وتعديل الأدوار.
9. **تحسينات أخرى:**
   - إضافة ملاحظة لاستشارة مقفلة.
   - تشفير الحقول الحساسة.
   - النسخ الاحتياطي.
   - الامتثال للقانون 09-08.
